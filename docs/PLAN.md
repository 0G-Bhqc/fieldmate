# research-harness —— 科研过程框架 · 规划文档

> 版本 v0.1（规划阶段）
> 定位：**作用于科研过程本身**的框架，可挂进 Agent Harness 使用。
> 与 `pfdenoise` 的关系：pfdenoise 降级为**能力③的实验后端**，不再是独立产品。

---

## 0. 立论

这个框架只主张一件事：

> **科研的复利不在读了多少论文，而在「已知缺陷清单」有多长，以及每读一篇是否往里加了一条。**

传统做法的复利来自「文献量」——但文献是可穷尽的，缺陷清单不是。
一个组如果维护一份 200 条的缺陷库，新人第一天就能避开 200 个坑，
这比让他读 200 篇论文的边际收益高一个数量级。

三个能力都是这个主张的函数：

| 能力 | 在框架里的角色 | 产出（复利资产） |
|---|---|---|
| ① 从旧论文缺陷找出精进点 | **入口**：读论文时做缺陷抽取 | 缺陷库新增条目 + 精进点候选 |
| ② 辅助理解透文献 | **放大器**：按阅读目的定制抽取深度 | 概念依赖图补边 + 方法卡补全 |
| ③ 辅助完成实验验证 | **兑现器**：把精进点变成可证伪的实验 | 预注册记录 + 负结果入库 |

**闭环：** ①产出精进点 → ③验证 → 无论正负结果都回写缺陷库 → ②使下次读同类论文更快更准。

## 1. 核心设计原则：判定归脚本，判断归 Prompt

这是整个框架最重要的工程约束，也是它能挂进 Harness 的前提。

| 类型 | 归属 | 例子 |
|---|---|---|
| 算、比对、校验、去重、schema 检查 | **脚本**（确定性，可测试） | 「这篇论文是否声明了噪声假设」「两次结果差多少」「CFL 是否超限」 |
| 抽取、归因、判断「这是不是缺陷」 | **Prompt**（judgment） | 「这句话是不是在承认一个未验证的假设」 |

**为什么这条必须硬性遵守：** Harness 里的 LLM 每次跑都可能不一样。
如果让模型去判断「这两个数字差 5% 还是 50%」，同一份代码两次评测结论会不一致，
框架就失去了可复现性——而可复现性是科研基础设施的最低要求。

推论：**所有指标、阈值、schema 校验都必须在脚本里，且必须有单元测试。**
Prompt 只允许产出「候选」，不允许产出「判定」。

```
                                    │                    └──────────┘
                                    ▼
                             ┌────────────┐

                             └────────────┘

```

### 2.1 四个目录的职责

| 目录 | 内容 | 谁维护 | 变更频率 |
|---|---|---|---|
| `contracts/` | 三个 JSON Schema：Paper / Defect / Experiment | 框架 | 极少 |
| `libraries/` | 缺陷库、概念依赖图、刊物画像、方法卡 | **使用者共同积累** | 高（这是核心资产） |
| `scripts/` | 确定性判定与计算 | 框架 | 中 |
| `prompts/` | 判断模板 | 框架 | 中 |

> **关键：`libraries/` 是数据不是提示词。** 它要被 grep、被版本控制、被 diff、
> 被多个 Agent 共享。放在 `prompts/` 里会导致它随对话上下文漂移、无法累积——
> 那就完全失去了复利意义。

## 3. 三个能力的设计

### 能力① 从旧论文缺陷找出精进点

**为什么现有做法不够：** 摘要式总结产出的是「这篇论文做了什么」，
而精进点需要的是「这篇论文**没验证什么**」，后者是摘要里系统性缺席的信息。

**做法：五槽抽取 + 缺陷库模式匹配**

每篇论文按固定 schema 抽成五条，**缺槽本身就是一个信号**：

```
Claim        它声称什么
Mechanism    靠什么机制实现
Evidence     用什么证据支撑（数据集/对照/指标）
Assumption   隐含但未验证的前提        ← 精进点的矿脉
Protocol     评测协议（噪声/分辨率/指标/基线）
Gap          作者自己承认的局限
```

然后拿 `Assumption` / `Protocol` / `Gap` 三槽去撞缺陷库：

- **命中已有模式** → 快筛，标记「本文疑似 D-EVA-001 体素化方法未报分辨率下限」
- **未命中** → 候选新缺陷，进入人工/Agent 审核 → 入库

**精进点的三个来源**（按可靠性排序）：
1. **作者自认的局限**（`Gap` 槽）——最可靠，直接可做
2. **缺陷库里同类缺陷在别处的解法**——跨论文迁移，例如「D-EVA-002 说明了 N2N 一致性的失效模式，
   那么在图像分割里做无标签评测时就可以直接引用这条」
3. **Assumption 未被任何人验证**——风险最高但价值也最高

**入库标准（防止库被垃圾污染）：**
- 必须写清 `detection` 字段（怎么自动发现）——**没有可检测方式的条目不准入库**，
  因为它无法被复用，只会变成又一篇需要人读的文档
- 必须有 `evidence`（来源：某论文某页 / 本地实测数据）
- `status` 区分 `verified`（本地复现过）/ `reported`（文献称述，未复现）

### 能力② 辅助理解透文献

**核心洞察：不该用同一套模板读所有论文。** 你从一篇论文里需要什么，
取决于你**读它干什么**。这是当前 LLM 论文助手的最大浪费——它对每篇都给同样的均匀深度。

**Purpose-driven reading modes：**

| 目的 | 必须抽到 | 明确可以跳过 |
|---|---|---|
| `implement` 复现 | 离散格式全文、参数表、初值、Δt、边界条件 | 动机、相关工作铺陈 |
| `beat` 超越 | Assumption、Protocol、缺陷库匹配结果 | 公式推导（除非要改） |
| `cite` 引用 | Claim、venue、定位 | 除此全部 |
| `build-on` 承接 | 接口约定、作者留的 open question、代码可得性 | 实验细节 |

**阅读顺序应该是拓扑序，不是任意序。** 由 `concept_graph.json` 决定：
```
偏微分方程 → 数值格式 → 双阱势 → Allen-Cahn → Cahn-Hilliard → 算子分裂 → 能量稳定性
```
新人默认从「Allen-Cahn」开始读，会卡在双阱势；拓扑序能省掉大量悬空概念。

**输出形态：渐进式披露**——第一层只给 Claim+Evidence（一屏读完），
需要哪槽再展开哪槽。避免把整篇塞进上下文。

### 能力③ 辅助完成实验验证

**这是最贵的环节，也是最容易被糊弄过去的环节。**
「代码跑通了」和「验证了主张」之间有巨大鸿沟。

**核心机制：实验预注册（pre-registration）**

在**跑之前**写下：

```json
{
  "claim": "相场去噪在保体积上优于拉普拉斯平滑",
  "metric": "rDrift",
  "baseline": "laplacian",
  "expected_direction": "|rDrift_pf| < |rDrift_lap|",
  "falsification": "若 |rDrift_pf| >= |rDrift_lap|，该主张被推翻",
  "confounds": ["体素分辨率", "噪声模型"],
  "res_floor_required": true
}
```

`exp_precheck.py` 校验：主张是否可证伪、指标是否被基线报告过、
必要的对照（`res_floor`、恒等基线）是否齐备。**不通过就不许跑。**

**为什么这条能救命：** 本会话我们自己的相场基准就撞上了这个场景——
我原本预期相场方法在 CD 上赢，结果它输了 5~7 倍。
如果事先预注册了「预期相场在保体积上赢、CD 上可能因分辨率受限」，
那么看到这个结果时就会**立刻判定为「符合分辨率受限的预测」**，
而不是浪费大量时间去怀疑实现有 bug（我确实浪费了）。

**负结果必须入库。** 实测发现的两个负结论（N2N 一致性被恒等变换奖励、
体素化方法须报分辨率下限）比任何正面结果都更有长期价值。
框架要有一条硬规则：**负结果不得被静默丢弃，也不许改指标去「让它看起来对」。**

## 4. Harness 集成契约

「能挂进 Harness」需要满足六条。这是本框架的工程验收标准。

| # | 要求 | 做法 |
|---|---|---|
| H1 | **无状态** | 框架不保存对话状态；所有持久化走文件系统（Harness 只管传路径） |
| H2 | **工具契约显式** | 每个 script 有 `--help`、明确 stdout schema、明确退出码；Harness 只需知道怎么调 |
| H3 | **判定可独立运行** | 脱离 LLM 也能跑（`pytest` 全绿即为证），所以结果可被第三方复核 |
| H4 | **Prompt 只产候选** | 见 §1。候选必须落盘为 JSON，经脚本校验后才进库 |
| H5 | **前/后置钩子** | 读论文前调 `defect_check`，实验前调 `exp_precheck`，实验后调 `result_diff` |
| H6 | **失败显式** | 所有退化/缺失抛错并给建议，禁止静默兜底（见缺陷库 D-REP-001） |

**具体到当前环境（Mavis / MiniMax Code）：**
最自然的落地形态是一个 **Skill**（`SKILL.md` + scripts），
这样 Agent 在做该领域研究任务时自动加载。
更重的形态是做成带 MCP 工具的 Plugin。
形态选择见 §7 待决项。

## 5. 现状：缺陷库已播种

`libraries/defect_patterns.jsonl` **不是示例，是本次会话实测验证过的真实数据**。
当前 **17 条**，校验结果（`detection` / `evidence` 字段零缺失）：

| class | 条数 | 代表 |
|---|---|---|
| `reproducibility` | 5 | 论文① λ 符号、Δt 量纲、论文② g 记号歧义、照印刷参数晶体反缩 |
| `evaluation` | 4 | 未报分辨率下限、N2N 一致性被恒等奖励、噪声分布不可迁移、点级配对失效 |
| `engineering` | 4 | 静默兜底、邻域偏移错向、亚格点量纲错、Hausdorff 单向索引 |
| `modeling` | 2 | 纯 AC 腐蚀液滴、目标场需 ±1 而非 0/1 |
| `discretization` | 2 | 时间步量纲、CH 四阶刚性 |

按状态：**`verified` 13 条 / `reported` 4 条**（前者本地复现过，后者仅文献称述）。
按严重度：**high 11 条 / medium 6 条**。

> **这份种子库本身就说明了框架的价值：**
> 其中 4 条（λ 符号、Δt 量纲、±1 编码、N2N 一致性）是我在复现两篇旧论文时踩到的，
> 如果新人一开始就拿到这份清单，能省下的是**几天的排查**，而不是几分钟。

值得单独指出：**`engineering` 类 4 条全部是「实现 bug 被误读成方法无效」**。
这类缺陷最贵——它们不报错，只是让结论反向。D-REP-001（静默兜底）我实际消耗了大量时间，
症状是「相场所有指标与不做处理完全一致」，看起来像「相场没用」而不是「代码有 bug」。
这正是 R1 风险的极端形态：**缺陷库本身也要能挡住「错误的结论」，而不只是记录「正确的做法」。**

## 6. 建设路线

### 方向修订（v0.1 → v0.2）

用户的三点确认改变了 Phase 1 的形态：

| 确认 | 影响 |
|---|---|
| **做成开源项目，挂载到任意 Harness** | 核心**不能**依赖任何 harness 私有 API。解法：核心纯 CLI + JSON 输出，`adapters/` 只做薄封装 |
| **接入真实 arXiv 检索** | 框架从「读你给的论文」变成「自己找论文」，新增 `sources/` 模块 |
| **先横向对比** | Phase 1 的核心产出是**跨论文对比矩阵 + 缺陷统计**，不是单篇闭环 |

因此新增两层，且 **「LLM 是可选插件」成为硬约束**：

```
任何 Harness ──调用 CLI（stdin/stdout JSON）──► 核心 rharness（纯确定性）
                                                      │
                            LLM 抽取？ ──是──► 通过 --llm-cmd 注入任意 harness 的 LLM
                                              └─否──► 纯规则降级（永远可用）
```

> 这条约束对开源项目是生死线：**在没有任何 LLM 的环境里也必须能跑出横向对比**，
> 接上 LLM 只是「抽得更准」，不是「才能用」。使用者不该先配好模型才能试。

### Phase 1 · 横向对比优先（v0.2 重排）

**目标：对一个研究方向给出「方法 × 维度」对比矩阵 + 缺陷统计报告。**

| 任务 | 产出 | 验收 |
|---|---|---|
| T1 `contracts/detection_rules.json` | 把 17 条缺陷的 `detection` 变成**机器可执行**的检测规则 | 规则能被纯 Python 求值，无 LLM |
| T2 `rharness/sources/arxiv.py` | arXiv Atom API 检索（分页、时间窗、去重、限速） | `all:"mesh denoising"` 取回 ≥20 篇 |
| T3 `rharness/sources/local.py` | 本地 PDF/目录（pypdf 优先，fitz 兜底） | 能解析工作目录里的 PDF |
| T4 `rharness/extract/metadata.py` | **L1 规则抽取**（title/abstract/venue/year/category） | 无 LLM 可跑，有单元测试 |
| T5 `rharness/match/patterns.py` | 缺陷库加载 + 规则匹配 → 每篇的缺陷标签 | 对真实 arXiv 结果能标出若干条 |
| T6 `rharness/compare/matrix.py` | **横向对比矩阵**（方法 × 维度） | 输出 Markdown 表 + JSON |
| T7 `rharness/compare/report.py` | 缺陷统计报告（含「未报告某项」的分母统计） | 方法学论文的典型形态 |
| T8 `rharness/llm/` | `LLMProvider` 协议 + `null` 降级 | `--llm none` 全流程可跑 |
| T9 `adapters/` | Skill / MCP server / 裸 CLI 三种挂载方式 | 至少 Skill + MCP 两个可用 |

**Phase 1 明确不做：** L2 全文槽位抽取（依赖 LLM，二期）、concept_graph、刊物画像、
方法卡、实验预注册（`exp_precheck` 挪到 Phase 2，因为它需要 Phase 1 的对比矩阵作基线）。

> 顺序理由：**「横向对比」先于「单篇深读」**，因为对比矩阵本身就是发现缺陷的
> 最强工具——一旦看到「20 篇里有 17 篇没报分辨率下限」，单篇深读就没必要了。
> 这也正是「跨论文缺陷统计」被提升为 Phase 1 的原因。

### Phase 2 · 深度与闭环

| 任务 | 产出 |
|---|---|
| T10 L2 全文五槽抽取（接 LLM） | Assumption / Protocol 槽，深度缺陷分析 |
| T11 实验预注册 + `exp_precheck` | 能力③；基线数据来自 Phase 1 的对比矩阵 |
| T12 `result_diff` | 正/负结果都报告，负结果回写缺陷库 |
| T13 缺陷库增长 CLI | 让「加一条」成本 <1 分钟 |

### Phase 3 · 规模化与协作

| 任务 | 产出 |
|---|---|
| T14 concept_graph | 驱动阅读顺序 |
| T15 期刊画像 | 每本刊偏好什么贡献类型 |
| T16 多源检索（Semantic Scholar / Crossref / 本地库） | 覆盖面 |

## 7. 风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 缺陷库退化成「没人读的长文档」 | 硬性要求 `detection`；**v0.2 起要求可执行**（T1），没有可执行检测的条目不准入库 |
| R2 | 库被单一子领域的模式污染 | `applies_to` 标注适用域；跨域迁移要求重新验证 |
| R3 | LLM 抽取不稳定 | §1 判定/判断分离；候选必须过 schema；且**无 LLM 也能出结果** |
| R4 | 变成「为了框架而框架」 | 每个任务都有验收标准；Phase 1 的「不做清单」已明确 |
| R5 | 与已有工具重复 | 刻意不做可微模拟、不做学习式去噪 |
| R6 | **arXiv 覆盖不全**（大量期刊论文不在 arXiv） | 报告必须标注「来源=arXiv，覆盖 N 篇」；期刊论文靠 `local.py` 补。这是方法学论文的常见软肋，必须自己先说出来 |
| R7 | 检索结果领域漂移 | 检索 query 可审计且落盘；对比报告附完整 query |
| R8 | 「横向对比」变成堆指标 | 矩阵必须有**可解释的维度**（方法族/评测协议/是否报分辨率/是否可复现），不是纯数字表 |

## 8. 明确的非目标（v0.2 增补）

| 非目标 | 原因 |
|---|---|
| 不做通用文献管理（Zotero/Mendeley 类） | 那些做「存」，我们做「判断」 |
| 不做全文语义检索 | 需向量库与 embedding 依赖，破坏「纯 stdlib 可跑」 |
| 不追求覆盖所有研究方向 | 宁可在一个方向做到「结论可发表」，也不做十个方向的浅尝 |
| 不做 LLM 微调 / prompt 工程优化 | LLM 是可插拔的外部依赖，框架不假设它的存在或能力 |
